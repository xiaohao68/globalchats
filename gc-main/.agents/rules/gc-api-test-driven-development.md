# Test-Driven Development (TDD) - 强制要求

## 概述

**gc-api 开发必须遵循 TDD 流程。**

先写测试，观察失败，编写最少量代码使其通过。

**核心原则：** 如果你没有看到测试失败，你不知道它是否测试了正确的东西。

**违反规则的文字就是违反规则的精神。**

## 何时使用

**始终必须：**
- 新功能
- Bug 修复
- 重构
- 行为变更

**例外（需人类确认）：**
- 一次性原型
- 生成的代码
- 配置文件

## 铁律

```
没有失败的测试就不能写生产代码
```

在测试之前写代码？删除它，重新开始。

**没有例外：**
- 不要保留作为"参考"
- 不要在写测试时"改编"它
- 不要看它
- 删除就是删除

从测试重新实现。就是这样。

## Red-Green-Refactor

### RED - 写失败的测试

编写一个最小的测试来展示应该发生什么。

**要求：**
- 一个行为
- 清晰的名字
- 真实代码（除非不可避免，否则不使用 mock）

### Verify RED - 观察它失败

**强制。从不跳过。**

```bash
pnpm test path/to/test.test.ts
```

确认：
- 测试失败（不是错误）
- 失败消息是预期的
- 因为功能缺失而失败（不是拼写错误）

**测试通过了？** 你在测试现有行为。修复测试。

### GREEN - 最少量代码

编写最简单的代码来通过测试。

不要添加功能、重构其他代码或超越测试"改进"。

### Verify GREEN - 观察它通过

**强制。**

```bash
pnpm test path/to/test.test.ts
```

确认：
- 测试通过
- 其他测试仍然通过
- 输出干净（无错误、无警告）

### REFACTOR - 清理

仅在 green 之后：
- 消除重复
- 改进名称
- 提取辅助函数

保持测试 green。不要添加行为。

### 重复

下一个失败测试对应下一个功能。

## 好的测试

| 质量 | 好 | 坏 |
|------|-----|-----|
| **最小化** | 一件事。名字中有"and"？分开。 | `test('validates email and domain and whitespace')` |
| **清晰** | 名字描述行为 | `test('test1')` |
| **展示意图** | 展示期望的 API | 掩盖代码应该做什么 |

## 为什么顺序重要

"我写完再写测试"

写完代码后测试立即通过。立即通过证明不了什么：
- 可能测试了错误的东西
- 可能测试了实现而非行为
- 可能遗漏了你忘记的边缘情况
- 你从未见过它捕获 bug

测试优先迫使你看到测试失败，证明它确实测试了某些东西。

## 常见借口

| 借口 | 现实 |
|------|------|
| "太简单不需要测试" | 简单代码也会坏。测试只需 30 秒。 |
| "我之后会测试" | 测试立即通过证明不了什么。 |
| "之后测试也能达到同样目标" | 之后测试 = "这做什么？" 测试优先 = "这应该做什么？" |
| "我已经手动测试过了" | 临时测试 ≠ 系统化。无记录，无法重跑。 |
| "删除 X 小时的工作是浪费" | 沉没成本谬误。保留无法信任的代码是技术债务。 |
| "保留作为参考，先写测试" | 你会改编它。那就是之后测试。删除就是删除。 |
| "需要先探索" | 可以。抛弃探索，用 TDD 开始。 |
| "测试难 = 设计不清晰" | 倾听测试。难测试 = 难使用。 |
| "TDD 会拖慢我" | TDD 快于调试。务实 = 测试优先。 |
| "手动测试更快" | 手动无法证明边缘情况。每次修改你都会重新测试。 |
| "现有代码没有测试" | 你在改进它。为现有代码添加测试。 |

## 红线 - 停止并重新开始

- 代码在测试之前
- 测试在实现之后
- 测试立即通过
- 无法解释为什么测试失败
- 测试是"之后"添加的
- 合理化"就这一次"
- "我已经手动测试过了"
- "之后测试达到同样目的"
- "这是关于精神不是仪式"
- "保留作为参考"或"改编现有代码"
- "已经花了 X 小时，删除是浪费"
- "TDD 是教条的，我是务实的"
- "这不一样因为..."

**所有这些意味着：删除代码。用 TDD 重新开始。**

## 示例：Bug 修复

**Bug:** 接受空邮箱

**RED**
```typescript
test('rejects empty email', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
```

**Verify RED**
```bash
$ pnpm test
FAIL: expected 'Email required', got undefined
```

**GREEN**
```typescript
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Email required' };
  }
  // ...
}
```

**Verify GREEN**
```bash
$ pnpm test
PASS
```

**REFACTOR**
如需要，提取多个字段的验证。

## 验证清单

在标记工作完成之前：

- [ ] 每个新函数/方法都有测试
- [ ] 在实现之前观察每个测试失败
- [ ] 每个测试因为预期原因失败（功能缺失，不是拼写错误）
- [ ] 编写最少量代码通过每个测试
- [ ] 所有测试通过
- [ ] 输出干净（无错误、无警告）
- [ ] 测试使用真实代码（mock 仅在不可避免时使用）
- [ ] 覆盖边缘情况和错误

不能勾选所有框？你跳过了 TDD。重新开始。

## 调试集成

发现 bug？写一个复现它的失败测试。遵循 TDD 周期。测试证明修复并防止回归。

永远不要在没有测试的情况下修复 bug。

## 测试反模式

添加 mock 或测试工具时，阅读 [.rules/testing-anti-patterns.md](.rules/testing-anti-patterns.md) 避免常见陷阱：
- 测试 mock 行为而非真实行为
- 向生产类添加仅测试的方法
- 不理解依赖就 mock

## 最终规则

```
生产代码 → 存在测试且先失败
否则 → 不是 TDD
```

未经人类许可没有例外。
